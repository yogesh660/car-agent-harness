01 / The problem

Buyers think in
sentences.

Marketplace search speaks in filters. A chat assistant closes that gap, but only if it can be trusted.

"A diesel estate under 15,000 with low mileage near Munich." "Is this one overpriced?" Today the buyer translates that into a dozen filters, and price judgement is a gut feeling.

An LLM assistant looks like the obvious fix. It brings two problems a marketplace can't ship with:

It makes things up. An invented listing, price or "fair deal" verdict is worse than no assistant, because the buyer acts on it.

It is hard to change safely. Prompts, tools and models change weekly, more and more often through coding agents. Without measurement, every change is a guess and quality drifts unnoticed.

02 / Approach

Three moves.

Grounding, measurement and a repo that agents can work in. Each one addresses a specific way this kind of system fails.

01

Answer only from data

The LLM never answers from memory. It turns a question into calls to typed tools that read the listings database: search, price estimate from comparable cars, side-by-side comparison. Unknown arguments are rejected, not ignored.

02

Measure every change

56 ground-truth questions check that the right tools were called with the right arguments, and that every price, mileage and listing id in the answer came from a tool result. A regression blocks the change.

03

A repo built for agents

Written rules (CLAUDE.md), one command for everything, decision records and tests that check the repository itself, so a coding agent can make a change, prove it's safe and open a reviewable PR.

03 / Architecture

Models propose,
code decides.

The language model chooses which tool to call and how to phrase the answer. Every fact comes from deterministic, tested code.

  1. The agent reads the question together with the JSON schemas of the three tools, and decides what to call.
  2. Tools validate their input. A made-up argument is an error the model sees and corrects, not something silently dropped.
  3. Price estimates are statistics, not opinions: the median of comparable cars, loosening the match until at least five exist, with a 25th-75th percentile band.
  4. The loop has a hard step budget, so a confused model stops with a clear message instead of spinning.
04 / Design principles

Decisions,
written down.

The reasoning behind each lives in the repository's decision records, next to the code.

01

Models propose, code decides

Facts, prices and verdicts come only from tested code. The model's job is choosing tools and writing the answer.

02

Measure before you change

No prompt, tool or model change goes in on a hunch. A prompt tweak that looked like a fix but lowered tool accuracy was reverted.

03

Fail loudly

Unknown tool arguments are rejected; an answer with an untraceable number fails the eval; a nightly regression opens an issue.

04

Portable by default

The model is an environment variable, the database a connection string, the service a container. Cloud choice stays a cost decision.

Trade-off

Synthetic data

2,500 generated listings keep the project self-contained and evals stable. Real data is a loader away.

Trade-off

Strict scoring

A different but reasonable filter counts as a failure. Accepted for stable, explainable numbers.

Trade-off

Small model baseline

Qwen 2.5 7B on CPU is free to run nightly and exposes real failure modes; larger models are one variable away.

Out of scope

Not a product

No accounts, payments or real listings. The point is grounding, evaluation and agent-ready engineering.

say so far.

The full 56-question suite runs nightly; its trend over time will be added once a few nights of runs exist.

Fixed

Silently ignored arguments

The model passed year=2020, which isn't an argument. It was dropped without an error, so the model believed it had filtered by year. Tool inputs now reject unknown arguments, and a repository check keeps it that way.

Open

Invented filters

For "automatic SUV, 2020 or newer, max 30k" the model adds a make and model the user never asked for.

Open

Dropped asking price

"Seller wants 18,500 ... fair price?" gets an estimate but no verdict, because the asking price isn't passed on.

Learned

Prompt rules are not free

Rules that fixed the asking price made the model skip the price tool elsewhere; tool accuracy fell from 100% to 92%. Reverted. The next lever is a stronger model or a router, not rules tuned on 13 questions.

Scorecard: current agent vs a prompt experiment
